# Setup and Deployment

How to run the classmate directory locally, where every setting lives, and how to operate production: deploys, the first admin, secret rotation, backups, and incident response.

## Local development

Requirements: Node 24 or newer (`.nvmrc` pins 24 for CI and Vercel), npm, and Docker. On WSL, enable Docker Desktop's WSL integration so `docker info` works inside the distro.

```bash
npm install
npx supabase start          # local Postgres, Auth and REST on 127.0.0.1:54321
npx supabase db reset       # apply migrations and load supabase/seed.sql
```

Create `.env.local` (git-ignored) from `.env.example`:

```bash
npx supabase status -o env  # prints API_URL, PUBLISHABLE_KEY and SECRET_KEY for the local stack
```

| `.env.local` variable | Local value |
|---|---|
| `SUPABASE_URL` | `API_URL` from `supabase status` |
| `SUPABASE_PUBLISHABLE_KEY` | `PUBLISHABLE_KEY` from `supabase status` |
| `SUPABASE_SECRET_KEY` | `SECRET_KEY` from `supabase status` |
| `CLASS_PASSCODE_HASH` | `printf 'local-class-passcode' \| node scripts/hash-passcode.mjs` |
| `SESSION_SECRET` | `openssl rand -base64 48` |
| `RATE_LIMIT_SALT` | `openssl rand -hex 24` |
| `NOMINATIM_CONTACT_EMAIL` | your email (sent to Nominatim in the User-Agent) |

Then run `npm run dev` and open <http://localhost:3000>. The e2e tests assume the passcode `local-class-passcode`; override it with `E2E_PASSCODE`.

The seed creates six fictional classmates and two local-only Supabase Auth accounts:

| Account | Password | Purpose |
|---|---|---|
| `admin@classnet.test` | `local-admin-password` | Admin. Sign in at `/admin/login` to use the console. |
| `viewer@classnet.test` | `local-viewer-password` | Test-only. Used by `e2e/admin-access.spec.ts` to prove that a valid Supabase account without an `admins` row is refused at `/admin/login`. |

Classmates have no accounts and no login. They open the directory with the class passcode at `/unlock`. The only login is the admin login. The `viewer@` account is not a classmate login or a user role. It only stands in for a Supabase account that exists but is not an admin, such as a user created in the dashboard without the `admins` insert.

`supabase db push` never applies `seed.sql`, so these accounts never exist in production.

### Checks

| Command | What it runs |
|---|---|
| `npm run lint` | ESLint, including the rule that rejects any `process.env.NEXT_PUBLIC_*` reference |
| `npm run typecheck` | `next typegen` and `tsc --noEmit` |
| `npm test` | Vitest unit tests |
| `npm run db:test` | pgTAP tests in `supabase/tests/` (needs the local stack) |
| `npm run build` | production build (needs no env vars) |
| `npm run scan:bundle` | fails if a Supabase URL or key, a JWT, or a configured secret value appears in the browser bundle |
| `npm run test:e2e` | Playwright against `next start` (or a server already on port 3000) with the seeded local stack |

`predev` and `prebuild` copy MapLibre's worker into `public/maplibre/` (git-ignored); see `scripts/copy-maplibre-worker.mjs`.

## Configuration reference

Production infrastructure is code. The Terraform module in `infra/` owns the Supabase project and its Auth and API settings, the Vercel project with its env vars and domain, and the GitHub `production` environment. State lives in the HCP Terraform workspace `classmate-directory-production`. Do not change a Terraform-managed setting in the Supabase, Vercel or GitHub dashboard: the next deploy applies Terraform first and reverts it. Change `infra/` in a pull request instead.

The app reads only server-side variables, validated in `src/lib/env.ts`. None use the `NEXT_PUBLIC_` prefix, so none reach the browser. Terraform sets all of them on the Vercel project for Production. Credentials use Vercel's Secret type, which cannot be read back.

| Variable | Required | Source of the production value |
|---|---|---|
| `SUPABASE_URL` | yes | derived from the Terraform-created Supabase project |
| `SUPABASE_PUBLISHABLE_KEY` | yes, server-side only | the project's default publishable key, read by Terraform (Secret) |
| `SUPABASE_SECRET_KEY` | yes (`sb_secret_…`, bypasses RLS) | the Terraform-managed key `vercel_server` (Secret) |
| `CLASS_PASSCODE_HASH` | yes, `scrypt:N:r:p:salt:hash` | HCP variable `class_passcode_hash` (Secret) |
| `SESSION_SECRET` | yes, at least 32 bytes | generated by Terraform, rotated by `session_secret_version` (Secret) |
| `PASSCODE_SESSION_DAYS` | no, default `30` | `passcode_session_days` in `infra/production.auto.tfvars` |
| `RATE_LIMIT_SALT` | yes, at least 16 characters | generated by Terraform, rotated by `rate_limit_salt_version` (Secret) |
| `NOMINATIM_CONTACT_EMAIL` | yes | `nominatim_contact_email` in `infra/production.auto.tfvars` |
| `GEOCODE_COUNTRY_CODES` | no, default `vn` | `geocode_country_codes` in `infra/production.auto.tfvars` |

Production Auth and API settings, such as signups being off and the 12-character minimum password, come from `infra/supabase-settings.json`. `scripts/supabase-settings-parity.test.ts` (part of `npm test`) keeps that file equal to `supabase/config.toml`, so local and production behave the same. Only `site_url` and the empty redirect allow-list are production-only, set in `infra/supabase.tf`.

Terraform also writes the GitHub `production` environment that `.github/workflows/deploy.yml` reads:

| Secret | Purpose | Source |
|---|---|---|
| `SUPABASE_ACCESS_TOKEN` | Supabase CLI access (account token) | HCP variable `supabase_access_token` |
| `SUPABASE_DB_PASSWORD` | production database password, for `link`, `db dump` and `db push` | generated by Terraform |
| `SUPABASE_PROJECT_ID` | project ref | the Terraform-created project |
| `BACKUP_PASSPHRASE` | encrypts the pre-migration backup | HCP variable `backup_passphrase` |
| `VERCEL_TOKEN` | Vercel CLI deploys | HCP variable `vercel_api_token` |
| `VERCEL_ORG_ID` | Vercel team | `vercel_team_id` in `infra/production.auto.tfvars` |
| `VERCEL_PROJECT_ID` | Vercel project | the Terraform-created project |

The environment variable `PRODUCTION_URL` (`https://<production_domain>`) is the URL the smoke test checks.

The only hand-set GitHub secret is the repository secret `TF_API_TOKEN`, an HCP Terraform team token for this workspace. Every credential is stored once, as a sensitive variable on the HCP workspace:

| HCP Terraform variable (sensitive) | Value |
|---|---|
| `vercel_api_token` | a Vercel token for the team in `vercel_team_id` |
| `supabase_access_token` | a Supabase account access token |
| `github_token` | a fine-grained PAT for this repository only: Environments, Secrets and Variables (read and write), Metadata (read) |
| `class_passcode_hash` | output of `node scripts/hash-passcode.mjs` |
| `backup_passphrase` | a long random passphrase (for example `openssl rand -base64 32`), also kept in the maintainer's password manager so backups stay decryptable without HCP |

The repository is public. Anyone signed in to GitHub can read its Actions logs and download its artifacts, including the encrypted `db-backup-<sha>` files. The backup's only protection is `backup_passphrase`, so never use a memorable one. Terraform and the CLIs redact every sensitive value from the logs.

## First-time production setup

1. **Accounts and tokens.** Create a Supabase organization, a Vercel team, and an HCP Terraform organization (`nhatnam1507`, named in `infra/versions.tf`). Create the Supabase access token, the Vercel token and the fine-grained GitHub PAT from the table above. The GitHub repository must exist first.
2. **HCP workspace.** In HCP Terraform, create a CLI-driven workspace `classmate-directory-production` with Remote execution and Terraform 1.17.0, and restrict team access to the maintainer. Add the five sensitive Terraform variables above. Generate the passcode hash with:

   ```bash
   node scripts/hash-passcode.mjs   # prompts twice; the passcode never lands in shell history
   ```

3. **Non-secret inputs.** Fill in `supabase_organization_id`, `vercel_team_id`, `production_domain` and `nominatim_contact_email` in `infra/production.auto.tfvars`. The other values are already committed.
4. **Domain.** Buy the domain on Vercel, or point its nameservers at Vercel, under the same team. Attaching it to the project then configures the DNS records automatically.
5. **CI token.** Create an HCP team token with access to this workspace only, and store it as the repository secret `TF_API_TOKEN` (`gh secret set TF_API_TOKEN`).
6. **First apply.** Run `terraform login`, then `terraform -chdir=infra init` and `terraform -chdir=infra apply`. Review the plan before approving: it creates the Supabase project (allow up to 15 minutes), the Vercel project and the GitHub environment. A second `terraform -chdir=infra plan` must report `No changes`.
7. **Deploy.** Push to `main`. See [Deploy pipeline](#deploy-pipeline).
8. **First admin.** Users are data, not infrastructure. In the Supabase dashboard, open Authentication → Users → Add user, then create a user with an email and a strong password (at least 12 characters). Then run in the SQL editor:

   ```sql
   insert into public.admins (user_id)
   select id from auth.users where email = 'admin@example.com';
   ```

   Remove an admin with `delete from public.admins where user_id = …`.

## CI pipeline

`.github/workflows/ci.yml` runs on every pull request and is called by the deploy workflow:

1. `npm ci`, lint, typecheck, unit tests (including the Auth settings parity test).
2. `supabase start`, `supabase db lint`, and pgTAP tests.
3. Build against the local stack with throwaway CI-only secrets.
4. Bundle key scan, then Playwright e2e tests. On failure the Playwright report is uploaded for 7 days.

`.github/workflows/infra-plan.yml` runs on pull requests that touch `infra/`: `terraform fmt -check`, `validate`, and a speculative HCP plan in the `Infra plan` check. Fork pull requests get no `TF_API_TOKEN`, so they skip the plan. A same-repository pull request's plan runs its code with the workspace credentials, so give write access only to trusted collaborators.

## Deploy pipeline

`.github/workflows/deploy.yml` runs on every push to `main`. It reruns CI, then applies infrastructure and deploys. The whole workflow is in the `production-deploy` concurrency group, so one run's apply and deploy never interleave with another run's:

1. **Infra.** `terraform apply` runs remotely in HCP Terraform. It writes the Supabase settings, the Vercel project and env vars, and the GitHub environment's secrets, and reverts any dashboard drift. If it fails, nothing deploys and production stays on the previous app and configuration.
2. **Backup.** It runs `supabase db dump` for the schema and for the data, tars both, and encrypts the archive with AES-256 using `BACKUP_PASSPHRASE`. Only the `.gpg` file is uploaded, as artifact `db-backup-<sha>`, kept for 7 days. If the backup fails, nothing is migrated.
3. **Migrate.** `supabase db push --linked --yes`.
4. **Build.** `vercel pull` and `vercel build --prod`, then the bundle scan on the prebuilt output. Vercel Secret values cannot be pulled, so the scan reads their literal values from the Terraform output `scan_literals`, masks them in the log, and fails if any is empty.
5. **Deploy.** `vercel deploy --prebuilt --prod`.
6. **Smoke test.** `/` must answer `307` to `/unlock` with `X-Robots-Tag: noindex, nofollow`.

Migrations are forward-only. Never edit an applied migration; add a new one.

To roll back a bad infrastructure change, revert its commit. The next push re-applies the previous values and redeploys.

**If HCP Terraform is unavailable**, deploys block at the infra job. In an emergency, deploy from a workstation with the values Terraform already wrote: run `supabase link`, `supabase db push` and `vercel deploy`, using the same commands as `deploy.yml`. Re-run the Deploy workflow once HCP is back, so Terraform and production agree again.

## Operations

### Rotate the class passcode

Generate a new hash with `node scripts/hash-passcode.mjs`, replace the HCP workspace variable `class_passcode_hash`, then rerun the latest Deploy workflow. It applies the new value and redeploys. The session cookie's signing key covers the passcode hash, so every existing viewer session stops working at once. Share the new passcode with the class.

### Rotate the session secret or the rate-limit salt

In a pull request, bump `session_secret_version` or `rate_limit_salt_version` in `infra/production.auto.tfvars` (both default to `1`). Merging it generates a new value and redeploys. A new session secret makes every viewer enter the passcode again; admin logins are unaffected. A new salt resets rate-limit buckets.

### Read the database password

`terraform -chdir=infra output -raw supabase_db_password` prints the generated password. Run it in a shell, keep the value in memory, and never paste it into a file. `npx supabase link --project-ref <ref>` and the restore below need it.

### Restore a backup

1. Download the `db-backup-<sha>` artifact from the Deploy run (Actions → run → Artifacts), and unzip it.
2. Decrypt and unpack it:

   ```bash
   gpg --decrypt db-backup-<sha>.tar.gz.gpg > backup.tar.gz   # prompts for BACKUP_PASSPHRASE
   tar xzf backup.tar.gz                                     # schema.sql and data.sql
   ```

3. Restore it into the project. For a full restore into an empty database, apply the schema first and then the data:

   ```bash
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f schema.sql
   psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f data.sql
   ```

   `DATABASE_URL` is the connection string from Supabase → Project Settings → Database, with the password from [Read the database password](#read-the-database-password). To roll back only the data after a bad migration, push a forward-fix migration first, then load `data.sql` into the emptied tables.
4. Delete the decrypted files. They contain classmates' personal data.

### A secret key leaks

`SUPABASE_SECRET_KEY` bypasses row-level security, so treat a leak as a full data exposure:

1. Replace the managed key and redeploy in one step: run `terraform -chdir=infra apply -replace=supabase_apikey.vercel_server`, then rerun the latest Deploy workflow. Terraform deletes the leaked key, creates a new one, and writes it to Vercel.
2. Rotate `SESSION_SECRET` and the class passcode if the leak may have included them (see above).
3. Review recent `change_requests` and `people` changes for tampering.

A leaked `SUPABASE_PUBLISHABLE_KEY` alone exposes nothing, because RLS gives the `anon` role no access. To rotate it, create a new publishable key and revoke the old one in Supabase → Project Settings → API Keys, then rerun Deploy: Terraform reads the current publishable key on every apply. Rotate a leaked `VERCEL_TOKEN`, `SUPABASE_ACCESS_TOKEN` or GitHub PAT at its provider, update the HCP workspace variable, and rerun Deploy.
